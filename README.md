# Huddle

A real-time community platform: servers, text and voice channels, roles and permissions,
DMs and group DMs, friends, voice/video/screen share, file sharing and notifications.
Product analysis and architecture: [docs/SPEC.md](docs/SPEC.md).

## Run it

Requires Node 24+. No database server or Docker needed (uses Node's built-in SQLite).

```bash
npm install
npm run seed -w @huddle/server   # demo users alice / bob / carol, password: password123
npm run dev                      # API on :3001, web on http://localhost:5173
```

Open http://localhost:5173 for the marketing site, or http://localhost:5173/login for the app.
To try two accounts at once, use two origins with separate storage, e.g.
`http://localhost:5173` and `http://127.0.0.1:5173`.

To fill Discover for local testing or a demo, run `npm run seed:demo -w @huddle/server`. It adds ~24 clearly
fictional public communities (generated banners and icons, a few messages each) and ~40 demo member accounts with
random, unprinted passwords. It is idempotent (communities that already exist by name are skipped), safe to run while
`npm run dev` is up, and **for local/demo use only**: it is not part of `npm run seed`, so a production deploy starts clean.

## Test

```bash
npm test          # 48 server tests (REST, gateway, permissions, voice signaling)
npm run typecheck
npm run build     # production web build -> apps/web/dist
```

Production: `npm run build && NODE_ENV=production npm start` serves the API and the built web app from one port.

## Layout

| Path | What |
|---|---|
| `packages/shared` | Wire contract: models, permission bitfield + algorithm, gateway opcodes/events, snowflakes |
| `apps/server` | Fastify REST API, WebSocket gateway, voice signaling, uploads, SQLite |
| `apps/web` | React app (`src/components`, `src/stores`), WebRTC engine (`src/voice`), marketing site (`src/landing`) |

## Voice & video across networks

Calls are peer-to-peer (WebRTC mesh, best for ≤ 8 people) and use public STUN. For users behind
strict NATs, set a TURN relay on the server with `HUDDLE_TURN_URL` plus either `HUDDLE_TURN_SECRET` (coturn
`static-auth-secret`: each signed-in user gets credentials that expire after 24 h) or a fixed
`HUDDLE_TURN_USERNAME` / `HUDDLE_TURN_CREDENTIAL`. Clients fetch them from `/api/ice` (sign-in required, no rebuild needed). Build-time
`VITE_TURN_*` in `apps/web/.env` still works as a fallback.
Camera, microphone and screen share require `localhost` or HTTPS.

## Stickers & GIFs

Stickers ship with a built-in pack, the "Huddle Buddies" (`apps/web/public/stickers/`, regenerated by
`node scripts/gen-stickers.cjs`). Members with **Manage Expressions** (the `MANAGE_EMOJIS` bit, which now
covers emoji and stickers) can upload up to 30 server stickers (PNG, APNG, GIF or WebP, ≤ 512 KB) under
Server Settings → Stickers. Join messages get a "Wave to say hi!" button that replies with the wave sticker.

The GIF picker is off until the server has a GIPHY key: create an app at developers.giphy.com (API
type; a beta key is fine for dev), copy `.env.example` to `.env` (repo root or `apps/server/`) and set
`HUDDLE_GIF_API_KEY=<key>`, then restart the server (it loads `.env` on start; in production set a real
environment variable). The picker shows "Powered by GIPHY" as GIPHY's terms require. The server proxies
`/api/gifs/search` and `/api/gifs/trending` (cached for a minute, rate-limited per user) and never sends
the key to clients; `/api/config` tells the web app whether to show the GIF button. Picked GIFs are sent
as the GIPHY media URL and render inline as an animated embed.

## Email (verification & password reset)

With SMTP configured, Huddle emails 6-digit codes to:

- **verify the email at sign-up** — new accounts can't use chat until they enter the code (they can resend it, fix a
  mistyped address, or log out). Accounts that existed before this feature are treated as verified.
- **reset a forgotten password** — "Forgot your password?" on the login page. Resetting signs out every other
  session and also verifies the email.
- **confirm a new email** in Settings → My Account — the address only changes once the code sent to it is entered,
  and the old address gets a notice. Changing the password in settings also signs out every other device.

Codes are valid for 10 minutes, allow 5 guesses, can be resent once a minute, and are capped per address and per IP
each hour. Only a keyed hash of each code is stored. Set the variables (repo-root or `apps/server/.env` locally, real
environment variables in production) and restart:

```sh
# Brevo (free tier, 300 emails/day): SMTP & API → SMTP keys
HUDDLE_SMTP_HOST=smtp-relay.brevo.com
HUDDLE_SMTP_PORT=587
HUDDLE_SMTP_USER=<your Brevo SMTP login>
HUDDLE_SMTP_PASS=<your SMTP key>
HUDDLE_MAIL_FROM=Huddle <no-reply@huddlechat.duckdns.org>   # a sender/domain verified in Brevo
HUDDLE_PUBLIC_URL=https://huddlechat.duckdns.org

# Gmail (small deployments): turn on 2-Step Verification, then create an app password
# at myaccount.google.com/apppasswords
HUDDLE_SMTP_HOST=smtp.gmail.com
HUDDLE_SMTP_PORT=465
HUDDLE_SMTP_USER=you@gmail.com
HUDDLE_SMTP_PASS=<16-character app password>
HUDDLE_MAIL_FROM=Huddle <you@gmail.com>
HUDDLE_PUBLIC_URL=https://huddlechat.duckdns.org
```

Port 465 uses TLS from the start; 587 requires STARTTLS. With a free sender address (no SPF/DKIM for your own
domain, e.g. on DuckDNS) some codes will land in Spam or Promotions; the code screens tell users to look there. Without `HUDDLE_SMTP_HOST` verification is off: new
accounts are created verified and the server logs a warning at boot. For local testing without a mail server,
set `HUDDLE_REQUIRE_EMAIL_VERIFICATION=1`: codes are then printed to the server console (never in production).
Seeded accounts (`npm run seed`) are always verified.

## Deploy

The `Dockerfile` builds one container that serves everything on port 8080. The host needs:

- **WebSockets** (the gateway at `/gateway`) and **HTTPS** (browsers block mic, camera and screen share otherwise).
- **A persistent volume at `/data`** for the SQLite database, uploads and the JWT secret.
  Without it every redeploy wipes all accounts and messages.
- One instance only: the realtime gateway keeps state in memory.

| Variable | Needed | Purpose |
|---|---|---|
| `HUDDLE_JWT_SECRET` | recommended | Login token signing key; otherwise generated into `/data` on first boot |
| `HUDDLE_TURN_URL` | for calls across networks | e.g. `turn:relay.example.com:3478,turns:relay.example.com:5349` |
| `HUDDLE_TURN_SECRET` | with TURN (recommended) | coturn `static-auth-secret`; Huddle issues 24 h credentials per user |
| `HUDDLE_TURN_USERNAME`, `HUDDLE_TURN_CREDENTIAL` | with TURN, no secret | Fixed relay login |
| `HUDDLE_GIF_API_KEY` | optional | GIPHY API key for the composer GIF picker (see above) |
| `HUDDLE_SMTP_HOST` | for email | SMTP server; setting it turns on email verification and password reset (see above) |
| `HUDDLE_SMTP_PORT` | with SMTP | `587` (STARTTLS, default) or `465` (TLS) |
| `HUDDLE_SMTP_USER`, `HUDDLE_SMTP_PASS` | with SMTP | SMTP login |
| `HUDDLE_MAIL_FROM` | with SMTP | Sender, e.g. `Huddle <no-reply@huddlechat.duckdns.org>` (must be allowed by your provider) |
| `HUDDLE_PUBLIC_URL` | with SMTP | The site address used in email links, e.g. `https://huddlechat.duckdns.org` |
| `HUDDLE_REQUIRE_EMAIL_VERIFICATION` | optional | `1` forces verification on without SMTP (dev only: codes print to the server console) |

**Railway or Fly.io** (both support volumes and WebSockets): create an app from this repo, let it
build the Dockerfile, attach a volume mounted at `/data`, set the variables above, and open the
generated `https://` address. **A VPS**: `docker build -t huddle . && docker run -d -p 8080:8080
-v huddle-data:/data --env-file .env huddle`, behind Caddy or nginx for HTTPS.

For TURN, a managed relay (Metered, Twilio, Cloudflare Calls) is quickest; self-hosting means
running coturn on a VPS with UDP 3478 and a relay port range open.
